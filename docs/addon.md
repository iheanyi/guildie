# Addon, desktop app and helper (proof of concept)

Blizzard updates a character's public profile only when they log out. The
addon and the desktop app let players who install them show changes sooner:
after a `/reload`.

Two programs do the uploading, with the same code (`packages/sync`):

- **The desktop app** (`apps/desktop`, Electron, Windows): Guildie in its own
  window; signing in there connects it. Replaces the helper.
- **The helper** (`apps/helper`, Bun): tray only, connects through the
  browser. Kept for now.

Below, "the helper" means either.

```
game ── addon saves GuildieDB ──▶ SavedVariables/Guildie.lua (on /reload, logout)
                                         │ desktop app (or helper) watches, uploads on change
                                         ▼
                    POST https://guildie.club/api/helper/snapshot  (Bearer gld_…)
                                         ▼
                         Convex helper:ingest ── addonSnapshots
```

## API

Connecting, desktop app: the user signs in in the app's window and the site
hands the app a token through `window.guildieDesktop.setToken` (the bridge,
apps/desktop/README.md); the app checks it with `/me` before keeping it. When
the site signs out it calls `signOut()`, which revokes the token. The pairing
below is the app's fallback.

Connecting, helper (no token to copy):

- `POST /api/helper/pair` `{ label }` → `{ code, pollSecret, connectUrl, expiresInSeconds }`.
  The helper opens `connectUrl` (`/helper/connect?code=…`); the signed-in player
  clicks Connect.
- `POST /api/helper/pair/poll` `{ code, pollSecret }` → `pending`, `expired`, or
  `approved` with the token (handed over once). Codes last 10 minutes.

The rest take `Authorization: Bearer gld_…`. Only the token's hash is stored;
an account keeps up to 10 (connecting an 11th retires the least recently
used); the account page lists them with Disconnect.

- `POST /api/helper/signout` → the token stops working.
- A 401 from `snapshot` or `guild-data` means the token was revoked (say from
  the account page): the helper and the app forget it and show "not connected".
- `GET /api/helper/me` → `{ battletag, characters }` or 401.
- `POST /api/helper/snapshot`, body (≤ 256 KB):
  `{ "version": 1, "characters": [ { "guid", "name", "level", "classToken", "capturedAt", "talents": [ { "id", "rank", "name" } ] } ] }`
  → `{ accepted: [slug], unmatched: [name] }`. `capturedAt` is game server
  time in seconds; talent `id` is the TraitDefinition ID. One upload per 5 s
  per token.

A character is accepted only if the token's owner claimed it: matched by
Blizzard's character id (the hex number at the end of the in-game GUID), or by
first name if exactly one claimed character has it.

## Desktop app bridge

The Guildie desktop app loads the site in its window and exposes a bridge
through Electron's `contextBridge`, on our own origins only:

```ts
window.guildieDesktop?: {
	isDesktop: true;
	version: string;
	getState(): Promise<{ connected: boolean; account?: string }>;
	setToken(token: string, account?: string): Promise<void>;
	signOut(): Promise<void>;
}
```

The web side (`apps/web/src/lib/desktop.ts`, `apps/web/src/components/desktop-bridge.tsx`,
mounted in `__root.tsx`):

- When the bridge exists, the player is signed in and `getState()` says not
  connected, the page calls `helper:issueDesktopToken({ label })` (signed-in
  user; label `Desktop app <version>`) and hands the token to
  `setToken(token, battletag)`. Once per signed-in user per page load. It's
  an ordinary `gld_…` token: same 10-per-account limit, listed on /me with
  Disconnect, used with the API above.
- "Sign out" on the site also calls `signOut()` on the bridge.
- Nowhere else issues tokens without the pairing code.
- Layout: the app appends ` GuildieDesktop/<version>` (and ` (Mica)` on
  Windows 11) to its user agent. The root route reads it during SSR
  (`readDesktopInfo` in `lib/desktop.ts`) and renders
  `<html data-desktop="true">` (and `data-material="mica"`), which switches on
  the title bar (`components/app-titlebar.tsx`), default cursors, and
  transparent chrome over Mica (`styles/app.css`). `useInDesktopApp()` is true
  from the first render when the user agent says so, and once mounted when only
  the bridge does (app builds before 0.2).

## Guild data in game (reagent tooltips)

The other direction. Addons can't use the internet: data reaches the addon only
as files that exist when the game loads (login, `/reload`). The tooltips work
from the addon alone; the Guildie app keeps them fresher. Three sources, and
for your current guild the addon uses whichever copy has the newest
`generatedAt` (`apps/addon/Guildie/Data.lua`):

1. **Bundled with the addon** (`GuildieBundle.lua`): every *public* guild, put
   in each release by `apps/addon/scripts/build.ts` from
   `GET /api/addon/bundle`. Released daily (below); CurseForge, Wago and WowUp
   update the addon by themselves, the way Raider.IO ships its data.
   Members-only guilds are never in it.
2. **From the Guildie app** (`GuildieData.lua`): the app downloads
   `GET /api/helper/guild-data?v=2` every 15 minutes (and on connect and
   "Upload now") and writes it into each installed copy of the addon. Only the
   guilds the token's claimed characters are in, so members-only guilds work.
   An addon manager's update replaces the folder; the app puts the file back
   within 30 seconds.
3. **Shared by a guildmate** (guild sync, `GuildieDB.shared` in
   SavedVariables): addons pass the newest copy around the guild in game, so
   one member with the app (or a fresh release) keeps everyone current. Below.

The addon finds your guild with `GetGuildInfo("player")` (retried on
`PLAYER_GUILD_UPDATE` / `GUILD_ROSTER_UPDATE`, since it's empty right after
login) and `GetCurrentRegion()` (1 us, 2 kr, 3 eu, 4 tw), keyed `region/slug`
with the server's `guildSlug`. Lua lowercases ASCII only, so a guild with
non-ASCII letters is also matched by name. Once it knows your guild it lets go
of the bundle's other guilds.

Tooltips: one line, skipping your own characters (the app's `mine`, plus
characters this account played with the addon): "**Guildie** might want this:
Brenna (Tailoring), Corwin (Alchemy) +2". For each reagent, guild members
whose known recipes use it, most recipes first (top 8). Built from Blizzard's
recipe catalog (`apps/web/convex/recipes.ts`, weekly) and each member's known
recipes (with their profile, hourly), per guild by `buildGuildEntries` in
`apps/web/convex/addon.ts`, which both endpoints use.

The window (`/guildie` or the minimap button) says which guild, how fresh, and
from where: "Reagent tooltips from the Guildie app, 2 min ago", "... shared by
Brisket, 1 hour ago", "... bundled with the addon, Nov 10". A guild with no
data anywhere: "MeowPewPew isn't on Guildie yet. Add it at guildie.club", with
the address in a box to copy (addons can't open a browser).

### Format (v2)

```lua
GuildieData = { -- GuildieBundle has the same shape, without `mine`
    version = 2,
    generatedAt = 1794329809505, -- ms
    mine = { "Brenna", "Alt" },  -- the app's player's characters
    guilds = {
        ["us/meowpewpew"] = {
            name = "MeowPewPew", region = "us", slug = "meowpewpew",
            generatedAt = 1794329809487,
            reagents = {
                [2589] = { name = "Linen Cloth", users = {
                    { name = "Brenna", classId = 8, profession = "Tailoring", recipes = 12 },
                } },
            },
        },
    },
}
```

`GET /api/helper/guild-data` without `?v=2` still returns v1 (every guild
merged: `{ version = 1, generatedAt, guilds = { names }, mine, reagents }`)
for Guildie app 0.2 and the helper, and the addon still reads a v1 file, for
its one guild only (a v1 file with several guilds can't say whose reagents are
whose). v1 data isn't shared by guild sync.

Both files are written as data literals only (`packages/sync/src/luaData.ts`,
tested), since the game runs addon files as code.

### Guild sync

Addon messages, prefix `Guildie`, `GUILD` channel (`apps/addon/Guildie/GuildSync.lua`):

```
H1 <key> <generatedAt>                                   I have this version (0: none)
S1 <id> <key> <generatedAt> <chunks> <bytes> <checksum>  a transfer starts
C1 <id> <n> <text>                                       chunk n (230 bytes of text)
```

- Each member announces `H` 15-45 s after login, again at about 5 minutes,
  then every 20 minutes.
- Hearing an older `H`, a member with newer data offers it after a random
  1-5 s, and stands down if someone starts sending that version (or newer)
  first. The same data isn't sent twice within 3 minutes.
- Hearing a newer `H`, a member with older data answers with its own `H`
  (2-8 s, skipped if someone already did), which prompts the newer one.
- Transfers go to the whole guild. One message per 1.2 s (about 200 bytes/s,
  under the game's per-prefix limit of a burst of 10 then 1 per second); a
  throttled message is retried. A guild of ~170 reagents is ~10 KB, under a
  minute.
- The text (`Wire.lua`) is compact (no reagent names; members and professions
  listed once) and printable ASCII. Received text is parsed by hand, never run
  (no `loadstring`): counts, sizes (128 KB), ranges and names (no `|` or
  control characters) are checked, and a checksum catches broken transfers.
- Kept only when the sender is in your guild roster, the key and the data's
  guild name and region are your guild's, `generatedAt` isn't in the future,
  and it's newer than what you have. Stored in `GuildieDB.shared[key]` with
  who sent it; dropped after 60 days without a refresh.
- Silent: no chat, no popups. `/guildie sync` shows a status line in the window
  and announces right away.

Tests: `luajit apps/addon/tests/run.lua [GuildieBundle.lua]` (LuaJIT or Lua
5.1; `brew install luajit`), against a stubbed WoW API with several clients on
one simulated guild channel: wire format and fuzzing, guild detection, source
picking, v1 files, tooltip lines, window text, and sync between clients
(including outsiders, other guilds, future dates and damaged transfers).

## Releases (CurseForge, Wago)

`.github/workflows/addon-release.yml`, daily at 05:17 UTC and by hand
(Actions → Addon release → Run workflow; or `gh workflow run addon-release.yml`):

1. `node apps/addon/scripts/build.ts` downloads `https://guildie.club/api/addon/bundle`,
   writes `GuildieBundle.lua`, sets `## Version` to `0.4.0-<yyyymmdd.hhmm>`
   (the `.toc`'s version plus the UTC date) and zips `Guildie/` into
   `apps/addon/dist/Guildie-<version>.zip`. It refuses a bundle with no guilds
   (`--allow-empty` overrides). Locally:
   `node apps/addon/scripts/build.ts --url https://<checkout>.guildie.localhost:1355`.
2. The zip is kept as a workflow artifact (30 days) every time.
3. If the addon's files or the data (timestamps aside) changed since the last
   upload, `apps/addon/scripts/upload.ts` uploads it to CurseForge and to Wago,
   each only when its secrets exist. A cache entry per uploaded hash
   remembers what went out. "force" uploads anyway.

The endpoint is cached: the Convex action keeps a build for 30 minutes
(`addonBundles` table and file storage, dropped when a guild turns
members-only) and the response is cached for 10 minutes. Scheduled workflows
run only on the default branch, so they start once this is merged to `main`.

### One-time setup

CurseForge:

1. Sign in at https://authors.curseforge.com (a CurseForge/Overwolf account).
2. Create a project: World of Warcraft → Addons, name "Guildie", a summary and
   description, license MIT. New projects are reviewed by CurseForge before
   they're public (usually a day or two); uploading the first file by hand
   from a workflow artifact is fine.
3. The **Project ID** is in the project page's "About Project" box.
4. API token: https://authors.curseforge.com/account/api-tokens → Generate.

Wago Addons:

1. Sign in at https://addons.wago.io.
2. Developer dashboard → create a project "Guildie" for WoW: Forever.
3. The **project ID** is the short id in the project's URL and settings
   (what packager calls `X-Wago-ID`).
4. API key: https://addons.wago.io/account/apikeys.

Then in GitHub, Settings → Secrets and variables → Actions → New repository
secret (or `gh secret set NAME`):

| Secret | Value |
|---|---|
| `CF_API_KEY` | the CurseForge API token |
| `CF_PROJECT_ID` | the CurseForge project ID (a number) |
| `WAGO_API_TOKEN` | the Wago API key |
| `WAGO_PROJECT_ID` | the Wago project ID |

Either pair alone works; without any, releases only go to the artifact. Then
run the workflow once by hand with "force". Optionally add
`## X-Curse-Project-ID: <id>` and `## X-Wago-ID: <id>` to `Guildie.toc`, which
helps addon managers match a hand-installed copy to the project.

The uploader matches the `.toc`'s interface (16001 → game version 1.60.1) to
CurseForge's WoW: Forever versions (type 88568) and Wago's `forever` patches,
like BigWigsMods/packager, falling back to the closest lower version.

## Which data wins

Per character, the addon's talents are shown only while its snapshot is newer
than the last time Blizzard's talents changed (`talentsChangedAt`, set by the
hourly sync). So:

- No addon: Blizzard's data, as today.
- Respec, then `/reload`: the addon's (page says "From the Guildie addon").
- Log out: Blizzard catches up to the same talents; if they differ, the newer
  one wins. A newer Blizzard change always takes over.

Addon data is player-provided; Blizzard's can't be edited by the player.

## Desktop app sign-in

Signing in never happens inside the app's window: Battle.net's "Sign in with
Google/Apple" can't run in an embedded browser. Instead:

1. The app (Sign in on the site, or the tray) starts pairing with
   `session: true` and opens `/helper/connect?code=…` in the player's browser.
2. They sign in there (any Battle.net login) and click Connect.
3. The app's poll returns its upload token and a one-time `sessionCode`
   (5 minutes, single use, hash stored in `desktopSessionCodes`).
4. The app opens `/desktop/session?code=…` in its window, which swaps the code
   for a normal session through the sign-in proxy (`auth:signInWithDesktopCode`)
   and goes on to the player's guild.
